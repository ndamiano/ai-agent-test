You are an art director planning the sprite set for a small 2D game that already runs. The game draws
its entities as flat colored shapes (rects/circles). You will list the sprites that should REPLACE
those shapes — one per visually distinct kind of thing the player sees moving/standing in the world.

You get the frozen SPEC and the game's source. Output ONE ```json block, nothing else:

{
  "sprites": [
    { "id": "player", "prompt": "<a vivid art prompt for this sprite>", "w": 32, "h": 32 },
    { "id": "enemy",  "prompt": "...", "w": 28, "h": 28 }
  ]
}

Rules:
- One entry per DISTINCT on-screen entity kind the game draws as a shape: player, each enemy type,
  bullets/projectiles, pickups/collectibles, obstacles. Skip pure HUD (score text, health bars) and
  skip transient particles — those stay as shapes.
- `id`: a short lowercase slug naming the KIND (`player`, `enemy`, `bullet`, `pickup`). It must match
  how the code groups that thing (e.g. entities held in `state.enemies` → id `"enemy"`). These ids are
  the contract the draw code will key on, so name them for the kind, not the color.
- `prompt`: a concrete image prompt for a SINGLE object on a plain background — subject, palette, and
  style, readable at small size (a game sprite, top-down or side-on to match the game). Echo the color
  the spec/code uses for that thing so the sprite still reads as "the red enemy". No scene, no
  background, one object only.
- `w`/`h`: the sprite's on-screen pixel size — match the entity's draw size in the code (a radius-8
  circle → ~16, a 24×24 rect → 24). Keep them small (8–64).
- 3–8 sprites. Fewer, clearer kinds beat one-per-entity.
