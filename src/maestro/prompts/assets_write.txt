You are writing the ASSET MANIFEST — the image plan for the game. Author it in ONE call:
write_component("asset_manifest", { ... }) in the shape the skeleton shows.

The CHARACTERS block holds the settled cast. Use its EXACT character ids — a character
entry here whose id doesn't match a `characters` component id is a bug.

HOLD ONE ART DIRECTION across everything — a single style, palette, and lighting — and
fold it into every description so the game looks coherent rather than like clip art from
five sources. Vary composition and framing per image (wide establishing shot vs. close
portrait vs. battlefield sprawl) — a shared palette should not mean a shared camera angle.

BACKGROUNDS — id prefixed `bg_`. Each description is a SELF-CONTAINED image-generation prompt
(2-3 sentences) that bakes in the style, palette, and lighting inline (the generator sees only
this text). ORDER MATTERS: name the room's CONTENTS first — furniture, objects, their state —
and put lighting/mood in the LAST sentence. The image model weights early words hardest and
truncates long prompts; a description that opens on mood renders an empty stylish room with
none of the objects (observed: "boxes stacked against walls" written after the mood clause
rendered as a bare neon room with one box). This manifest LOCKS once its checks pass — nothing written later can add a missing
location, so undercounting now forces every scene onto the same one or two rooms. The story and
places don't exist yet: read the SPEC's request paragraph for the settings it implies — a
single-location story legitimately needs one or two backgrounds; a story that moves between
named settings needs one per DISTINCT physical setting the request implies. Author a background
for each full-screen setting the game DISPLAYS: a point-and-click room, a full-screen story
scene, and a distinct COMBAT ARENA (one per encounter setting). Do NOT author a background per
walkable RPG zone — a world_map/town/interior map is drawn from its own tiles and shows no
backdrop image, so a per-zone `bg_` would be generated and never seen.

CHARACTERS — one per cast character, id EXACTLY matching the `characters` component id. The cast
card carries no appearance fields — invent hair, eyes, build, clothing, and distinguishing marks
yourself, grounded in the character's role/temperament/history and anchored to their card's
`color` as a visible accent (hair, eyes, or one clothing piece — an ordinary colored THING,
never "glowing"/emissive: the renderer takes that literally and everyday people end up wearing
light-up gear). Each character must read as visually distinct from every other in the cast —
not a recolor of the same base — and stay recognizable across scenes.

ITEMS — leave `items` as `[]`. Inventory/place items don't exist yet when this call runs; a
guessed id here matches nothing and only adds crossref churn.

CGS — the story doesn't exist yet, so you can't target real ending ids. If the request implies
a clear high point (a climax, a reveal, an ending), author one candidate CG for it, named for
the beat it serves (e.g. `cg_reveal`) — an unused CG costs nothing; a story peak with no CG is
the more common failure. A low-key single-scene game can leave `cgs` empty.

TITLE CARD — one hero image for the whole game, not a scene: a composition that reads the
premise at a glance (the cast, the central object, or the setting that most says what this game
is), same self-contained-prompt rules. Never describe text, logos, or title lettering in the
image — the renderer draws the title separately, and image models render text as garbage.
Commit explicitly to whether PEOPLE are in the frame: an object/setting composition must say
"no people" (the renderer invents a random person into any desk/room otherwise); a cast
composition names who and how they're posed.

Concrete beats mood-words: a named object, a specific quality of light, a particular palette
— never just "atmospheric" or "moody". No placeholders, no "TODO", no empty descriptions.
